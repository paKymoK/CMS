## 2. Gaps

### G1. Scheduling and Archive
- **Archive: done (posts).** Statuses are Draft, Published and Archived. Archived is off the site but kept, and can go back to Draft or be published again. The audit trail has an `ARCHIVE` action (archived back to draft is an update that lists the status change; publishing is still `PUBLISH`). **Archived posts stay editable (decision):** the status only controls whether the post is public, as with Draft and Private in WordPress, which has no built-in archived status and locks only Trash. Locking them would be a rule of our own: the server would reject content edits on an archived post and the editor would open read-only. Only posts may be archived; the server rejects ARCHIVED or any unknown status for the other content types. The Post editor has a three-way status switch, an **Archive** button (with a confirmation for a live post), **Save** and **Move to draft** for an archived post, and an "Archived" label in the list, Activity and search.
- **Public side:** an archived post answers "not found" like an unknown address and drops out of the public list and search with no read path changed (every public read matches `'PUBLISHED'` exactly). **Detail pages on the website are now fetched without Next's data cache** (`cache: "no-store"`): that cache only stores 200 responses, so a page that had been visited kept being served from its old copy after it was archived or unpublished. Lists keep the 60 s cache.
- **Schedule: done (posts), cron-based.** Statuses are now Draft, Scheduled, Published and Archived. The `active` flag is gone: status alone decides what is public (see "The `active` flag" below). See "Scheduled publishing" below.

**Scheduled publishing (built).**

- **Mechanism: pg_cron, once a minute.** The Postgres image already had pg_cron (`Dockerfile`, `postgresql.conf`: `shared_preload_libraries` and `cron.database_name = 'content'`). `init-schema.sql` now creates the extension and the job `publish-scheduled-content` (`* * * * *`, running `SELECT publish_scheduled_content()`). Once a minute was chosen over once a second to keep load low under pressure. The job is created only where pg_cron exists (the database named by `cron.database_name`); elsewhere (test databases, a managed Postgres without the extension) the schema still loads with a warning and scheduled items wait until the function is run some other way.
- **The function** `publish_scheduled_content()` moves due `SCHEDULED` items to `PUBLISHED` and due `PUBLISHED` items (with an `unpublish_at`) to `ARCHIVED`, clearing `unpublish_at`. Each direction is one `UPDATE` over a `FOR UPDATE SKIP LOCKED` selection: atomic, and a second runner skips rows the first holds. It takes everything overdue, so downtime or a missed run only delays publishing: seen live, after the machine slept for 14 minutes the job published and archived on its first run back. It stamps the write as the `System` user and bumps `version`, so Activity shows "System" and an editor with the item open gets the out-of-date-form warning.
- **Data:** `content_item.publish_at` / `unpublish_at` (timestamptz), checks (a scheduled item needs `publish_at`; `unpublish_at` must be later), and two small partial indexes so the minute check touches only waiting rows. The audit trigger has a `SCHEDULE` action and records both times (UTC) in the snapshots.
- **Rules (`ScheduleRules`):** posts only. Draft and Archived carry no times; Scheduled needs a future publish time (optional later unpublish time); a live post may have a future unpublish time. Times are kept to the minute. A time unchanged from what is stored is not re-checked against the clock, so saving in the minute before the job runs is not refused. A scheduled post without a display date is dated the day it goes live.
- **Editor:** a four-way status switch; for Scheduled a "Publish at" picker, for Scheduled and Published an optional "Take offline at" picker, with the editor's time zone shown (times are picked in it and stored as UTC). The main button reads Publish, Update, Schedule or Update schedule; publishing or scheduling a draft with SEO items missing asks once, as before. Labels for Scheduled are in the list, Activity and search.
- **Timing:** up to a minute for the job, plus the website's 60 s list cache; detail pages are not cached, so they appear as soon as the job runs.
- **Verified:** 129 content-service tests (new: `ScheduleRulesTest`, scheduling tests in `ContentAuditTriggerTest` that run the function against a real database, `StatusRulesTest`); the real pg_cron job published and archived a test row at the exact minutes; the editor was driven in a browser (schedule, SEO prompt, saved times, audit entry).
- **Browser checks, done:** on the website a scheduled post's detail page was a 404 while Scheduled, went to 200 in the same second the job ran, and was a 404 again within two seconds of its unpublish minute; the post list followed up to a minute later (its 60 s cache). The editor was checked at 820 and 390 px: the header buttons wrap, the status switch and pickers fit, nothing scrolls sideways. At 390 and 360 px the picker's popup was 515 px wide and ran off the left edge; a small-screen rule (`index.css`) now pins it to the left, lets it shrink and puts the time columns under the calendar.
- **Production:** not a concern yet, as the project has not gone live. If production Postgres is managed without pg_cron, the job must be set up there (or `publish_scheduled_content()` called by another scheduler); the schema loads either way but would only warn.
- **Trash is now built** (see G8). Other content types are not schedulable.

**The `active` flag (folded into status: done).** `content_item.active` is removed. What the public sees is now exactly `status = 'PUBLISHED'`: every public read, the search view and the full-text search dropped their `active` condition. An item that used to be inactive is simply a Draft (a post can also be Scheduled or Archived). In the admin the "Active" switches are gone from the Post, Case Study, page and list drawers; the list's old Active column is now a **Live** switch that flips Draft and Published (disabled for Scheduled and Archived posts, which are changed in the editor). The API no longer accepts or returns `active`; the audit snapshots no longer carry it. Two small behaviour changes: a case study's testimonial now shows only when the testimonial is **Published** (before, only active was checked, which the code comment already described as "unpublished quote omitted"), and restoring a version no longer restores an old active value. The seed data was unaffected (every seeded row is Published). The Banner's own "Active from / until" dates are separate fields in its data and are unchanged. The init SQL changed: recreate the local `content` database.

### G2. Categories and Tags management
**Built** (CAT-01 to CAT-06, TAG-01 to TAG-06), all five steps. Open: the public category URL redirect when a category is inactive (CAT-05, "ask Bảo": an inactive one answers "not found" for now).

**How it is stored (decisions).**
- A category and a tag are `content_item` rows of their own type (`post_category`, `post_tag`), **per site**, so the audit trail, addresses (a renamed one keeps its old address as an alias) and the Trash come from the generic machinery. Active is PUBLISHED and Inactive is DRAFT.
- A post stores **ids** (`categoryIds`, `tagIds`), so renaming never breaks it. The names the website and the search read (`category` = its first active category, `tags` = its active tags) are **derived** and kept in the post; they are rewritten whenever the post, or the category or tag, changes (rename, activate or deactivate, delete, restore). The website, the search and the list needed no change.
- Existing free-text categories and tags became rows: the seed (`init-data.sql`) creates "Uncategorized" for every site and, for English, the "Insight" category and three tags its posts used, and gives each post its ids. This edited both `init-schema.sql` (the address trigger now covers the two types) and `init-data.sql`: recreate the `content` database.

**Rules.** Name unique per site and kind (case-insensitive); the address is made from the name, editable, unique and normalised. A category has at most one parent, itself top-level; a child can be Active only while its parent is (deactivating a parent deactivates its children; activating a parent does not activate them). "Uncategorized" is the default: it cannot be deleted, deactivated, made a sub-category or moved to another address, and a post that would have no category gets it (it drops out as soon as the post has a real one). A post has at most **15 categories and tags together** (a server rule), only Active ones can be newly added (an inactive one a post already has stays), and unknown ids are refused. Deleting moves the item to the Trash (30 days): the posts that carried it lose it (a category's posts fall back to "Uncategorized"), a category's sub-categories become top-level, and a **restore** brings it back as Inactive with those posts and sub-categories. Posts are never deleted. "Remove from all posts" keeps the item.

**Admin.** Categories and Tags under Perspectives: search, status tabs with counts and a Trash tab, filters (parent), sort (name, updated, posts), 20 / 40 / 60 / All per page; create and edit in a side panel (name, slug that follows the name until typed, description, parent, active); row actions (edit, make active or inactive, remove from all posts, move to Trash); bulk make active, inactive and Trash with a per-item result; the **published-post count links to those posts** (zero is not a link). The post editor has pickers (chosen first, rest A to Z, "+ Create" on the spot which adds the new item to the post and keeps it even if the post is not saved, a shared n / 15 counter). The posts list filters by category and by tag, and the bulk bar has "Categories & tags" (add or remove one on the selected posts; a post at 15 is reported, the rest change). Search and Activity know the two types.

**Public site.** `/category/<slug>` and `/tag/<slug>` list the published posts that carry it (6 per page, newest first, the Insights cards); an inactive or unknown one is a 404. API: `GET /v1/post-categories[/{slug}]`, `/v1/post-tags[/{slug}]` (public in two places that must be kept in step by hand: core-v1 `SecurityConfig` and the gateway's `AuthenticationConfig`; restart the gateway after pulling).

**Verified.** 191 content-service tests pass (two existing test classes were adapted to the new signatures; no new unit tests, by decision). Against the real service and Postgres: create, duplicate name, sub-category depth, the 15 cap (16 refused, 15 accepted), unknown and inactive ids, keeping stored ids when a save leaves them out, deactivate and cascade, activating a child under an inactive parent refused, the default category's protections, Trash and restore (posts, a post's only category falling back to Uncategorized, a parent's children orphaned and re-linked), rename with the old address kept as an alias, a stale edit refused, bulk add and remove on posts, the id filter. In Chrome: the Categories, Tags and Trash screens, the edit panel, the editor's picker with inline create, the posts list filters and bulk bar. The public pages were checked against the running website (`/category/insight` 5 posts, `/tag/events` 4, an unknown or inactive one 404). **Not run in the browser:** the bulk "Categories & tags" dialog (its API was run).
**Not built:** a link from a post's category label to its page, and a "restore under another address" choice in the categories Trash (a clash is reported with the reason).

### G3. Post list view
Specified in POST-01. **Built** as a dedicated page (`/content/posts`, `PostsPage.tsx`) with a server-side list, so it stays fast however many posts a site has.
- **Table:** checkbox, Title (click opens the editor), Author, URL / slug (shortened, with a Copy URL button giving `https://<site domain>/<locale>/insights/<slug>`), Category, Tags, Updated (date and who, as `Display Name (sub)`), Status (Draft / Published / Scheduled / Archived, a scheduled post also shows when it goes live), and a row menu (Edit, Publish, Move to draft, Archive, Delete; a published post cannot be deleted).
- **Search** by title or slug: partial, any case, accents folded (`viet` finds `Việt`); a typed `%` or `_` is matched literally. **Filters** that combine: status tabs with counts, category (the values in use, with counts), month and year of the last update (UTC). **Sort:** updated newest or oldest (default newest), title A to Z or Z to A. **Clear filters** returns to the default list. **20 per page.** The state lives in the address (`?q=&status=&category=&month=&sort=&page=`), so a link or a return from the editor keeps it.
- **Bulk actions** on selected posts (up to 100, selection kept across pages): Publish, Move to draft (unpublish), Archive, through `POST /v1/admin/posts/bulk`. It uses the same rules and the same save as editing one post (validation, slug, dates, version, audit trail), one at a time; a post that cannot be changed (say, no title) is reported with its reason in a dialog and the others still go ahead; a post already in the status counts as done; only posts of the site are ever touched. A single row's menu uses the same call.
- **API:** `GET /v1/admin/posts/page?site&q&status&category&year&month&sort&page&size` (page counts from 1, size default 20, max 100), `GET /v1/admin/posts/facets?site` (status counts, categories in use, years), `POST /v1/admin/posts/bulk?site`.
- **Verified:** 42 API checks against 5,000 seeded posts, each compared with an independent SQL query (every filter and sort, paging, wildcard characters, SQL-looking input, other sites, facets); 25 bulk checks (statuses, audit rows, already-done, one bad post among good ones, another site's posts, bad input, access); 32 browser checks (search, tabs, filters, sort, paging, copy URL, bulk bar, the failure dialog, row menu archive and delete, switching site, phone width); 172 content-service unit tests (13 new). Median response over 5,000 posts: about 10 to 25 ms.
- **Trash: built** (G8): a Trash tab with its count, "Move to Trash" on the row menu and the bulk bar, Restore and Delete permanently. **Bulk assign category / tag: built (G2).** Previously noted as waiting: bulk **assign category / tag** and a category filter over real taxonomy (category is still a free text field and tags a plain list on each post, so the filter and column use those); the date filter is the last-update month (the BRD only says "Date (month/year)").

### G8. Delete rule and Trash
- **Delete rule: done (posts).** A published post cannot be deleted, from the API (400: "archive it or move it to draft first") or the list (the Delete button is disabled with a tooltip). Draft and archived posts can be deleted. The 051126 BRD no longer states this rule, but nothing contradicts it.
- **Trash with restore: built for posts** (051126 asks for it on Posts, Categories, Tags, Pages and Components; the mechanism is generic, so those switch it on when they are built).
  - **Design: a separate table, not a status.** `content_trash` holds the whole row as a JSON snapshot (plus its slug rows, aliases included). Moving a post there deletes it from `content_item`, so nothing that reads `content_item` (public pages, lists, search, counts, today's queries and every future one) has to remember to exclude the Trash, and a trashed post cannot be edited because it is simply not found. Chosen over a `TRASHED` status because a forgotten `WHERE` would show trashed items silently.
  - **Functions (init-schema.sql):** `trash_content_item`, `restore_trashed_item`, `delete_trashed_items`, `purge_trashed_content`. Each runs in one statement, so it is atomic.
  - **Rules:** a draft, scheduled or archived post can be trashed; a published one cannot (archive it or move it to draft first). Restore always gives a **Draft** with the same id and no schedule. The slug is free while the post is in the Trash; on restore its old addresses come back where still free.
  - **30 days:** nothing counts down. `trashed_at` is stored when the post goes in, and an hourly pg_cron job runs `purge_trashed_content()`, which deletes whatever is older than 30 days, as System, with a DELETE row in the audit trail. Catch-up by construction, so downtime only delays it. The list shows "N days left". Where pg_cron is missing (a plain test database) nothing purges until the function is run by hand, the same as scheduled publishing.
  - **Audit:** new actions `TRASH` ("Moved to Trash") and `UNTRASH` ("Restored from Trash"), same item id, so one post's history reads as one thread. A permanent delete (by hand) and the purge are `DELETE`. `RESTORE` stays for putting an old version back.
  - **Warnings (both are warnings, not blocks):**

### G13. User management and security (USR-01 to USR-07)
- **Decision: user management lives in auth-service, not in the admin app.** The Users screens (USR-01 to USR-05) are built there, next to the data they change. The admin app gets no Users module. It shows a link or redirect to auth-service for a user who has permission to manage users, and hides it for everyone else.
- What auth-service has today: REST endpoints for users, groups, departments, units, clients and project-scoped role assignments (`/v1/users`, `/v1/groups`, `/v1/clients/{clientId}/roles`, and so on). Its pages are only login, consent, profile-complete and error, so the Users UI itself is still to build there.
- **Done in auth-service (backend, first slice):**
  - **Management API locked down.** `/v1/**` was open to anyone at `:9000` (and any token holder through the gateway). It is now its own filter chain (`ApiSecurityConfig`): bearer token only, no session, and only an active **Super Admin** gets in. Super Admin = the global (no site) `ADMIN` role on `cms-admin`, held directly or through a group, on an account that is not inactive. It is read from the database on each call, not from the token, so a demotion or deactivation counts at once. The seed gives `admin` the global role at startup (no DB recreate needed).
  - **Read and status API:** `GET /v1/users` (search by name / email / username, filter by status, role, site; paging, max 100), `GET /v1/users/{sub}` (with cms-admin roles, direct and through groups), `PATCH /v1/users/{sub}/status` (`ACTIVE` / `INACTIVE`).
  - **Inactive means no login.** The state lives in `userinfo.status` (an existing, previously unused column; a missing value is ACTIVE). It cannot use `users.enabled`: LDAP shadow rows are created with `enabled = false`. The login check runs after the password check, covers LDAP and local accounts, and does not count toward the lockout. Deactivating also deletes the user's `oauth2_authorization` rows so refresh tokens stop working. An access token already issued stays valid for up to 15 minutes.
  - **Last Super Admin protected** (USR-03): deactivating the user, removing the role assignment, deleting the group, or removing the member is refused if it would leave no active Super Admin.
  - **MFA (USR-05): authenticator app (TOTP), optional per user, built.** Google Authenticator, Microsoft Authenticator and any RFC 6238 app work (SHA-1, 6 digits, 30 s, one step of clock drift). **Who:** any account (staff via LDAP, guests, administrators), by choice: **My profile → Two-step verification → Set up** shows a QR code (drawn in the service, the secret never goes to an outside site) and the text key; MFA turns on only after one correct code, then 10 one-time **recovery codes** are shown once. Turning it off or renewing recovery codes needs a current code (app or recovery). A Super Admin can **Reset** it on the user's page for a lost phone (turns it off, ends the person's sessions, audited). **Sign-in:** after a correct password, `TotpMfaPolicy` (replaces `NoMfaPolicy`) makes `DomainAuthenticationManager` throw `MfaRequiredException`; the browser goes to `/login/mfa`, the verified principal waits in the session (5 minutes, never in the security context, credentials erased) and the sign-in finishes with the same success handler only when the code passes, so the OAuth sign-in of the admin app resumes as before. This is not a failed login: no password-lockout count, no `LOGIN_FAILED`. **Safety:** secrets are encrypted (AES-256-GCM, bound to the account) with `AUTH_MFA_ENCRYPTION_KEY` (`openssl rand -base64 32`; empty = the feature is off and hidden; changing or losing the key makes stored secrets unreadable, so those people need an administrator's reset); a code works once (the accepted 30-second step is stored and updated atomically); wrong codes (any screen) share one counter `mfa-fail:<sub>`, 5 then a 10-minute lock, and a correct password does NOT reset it; with Redis down the lock is skipped, like the password lock. Audit: `MFA_ENABLED`, `MFA_DISABLED`, `MFA_RESET`, `MFA_FAILED`, `MFA_RECOVERY_USED`, `MFA_RECOVERY_RENEWED`. New tables `user_mfa`, `user_mfa_recovery` in `init-schema.sql`: recreate the `authentication` database. **Verified** (throwaway database, real LDAP, real browser, codes generated from the secret): setup with a wrong then a right code, sign-in with a wrong then right code, nothing reachable before the code (`/profile`, `/admin/users` redirect to `/login`), replay refused, lock after 5 and not reset by a new password step, a recovery code once, renew, turn off, admin reset ending sessions, OAuth `/oauth2/authorize` resumed to the callback after the code; 20 new unit tests (RFC 6238 vectors included). **Not done:** a real phone scan of the QR code (the QR holds the same `otpauth://` link as the text key, which the checks used); a guest and a local administrator signing in with MFA (same code path, not run separately); "required for a role" (a rule to add in `TotpMfaPolicy`); no admin-app (SPA) screen, MFA lives on the auth-service account pages; a lost key or lost phone plus lost recovery codes for the only Super Admin needs a database fix (`DELETE FROM user_mfa WHERE sub = '...'`).
  - **Verified against real Postgres and Redis** (service started, signed in through the OAuth login): 53 API checks, covering the list filters, deactivate and reactivate, refresh-token revocation, and the last-Super-Admin refusals by user, role, group and member. Unit tests: 16 (`ApiSecurityTest`, `UserServiceImplTest`, `DomainAuthenticationManagerTest`). Not run: the gateway path (Eureka was off). The inactive **LDAP** user case was later run against the local OpenLDAP (see the LDAP bullet below).
- **Done in auth-service (Users screens, Thymeleaf):** `/admin/users` (list with search and status / role / site filters, paging), `/admin/users/new`, `/admin/users/{sub}` (profile, CMS roles add and remove, deactivate and reactivate). The look follows the admin app (navy sidebar, light page, same tokens and fonts) and works at phone width. Only an active Super Admin gets in: not signed in goes to `/login` and back; signed in without the role sees a 403 page. Forms carry a CSRF token. The screens call the same services as the API, so the same rules hold (last Super Admin, inactive accounts). Checked in a browser: 29 checks at desktop width plus phone-width and access-denied views. `/admin` now redirects to the list (the old forward to a missing file is gone). ## 5b. Notice: CSP, HubSpot forms and SEO (plan only, not built)

The website has no Content-Security-Policy or security headers today (`frontend/website/proxy.ts` only does next-intl routing; `next.config.ts` sets no headers). **Nothing is implemented; recorded as a plan.**

**CSP and nonce**
- A nonce (random per request, in the header and on each trusted `<script nonce>`) stops injected scripts from running (XSS). It does not encrypt data or validate input. Pair it with `connect-src`, `form-action` and `frame-src` allowlists so a script that did run cannot send data to unknown hosts.
- Next.js 16: `proxy.ts` would generate the nonce, set the header and pass it on (`x-nonce`). Cost: pages using a nonce render dynamically, so static generation and CDN caching are lost for them.
- JSON-LD (`lib/seo/jsonld.tsx`) is a data block, not executable, so it needs no nonce.
- Third-party exceptions are explicit host allowlists, only for what is used: Google Analytics / Tag Manager (`www.googletagmanager.com`, `*.google-analytics.com`, `*.analytics.google.com`), HubSpot tracking if used (`js.hs-scripts.com`, `js.hs-analytics.net`, `*.hubspot.com`), and `frame-src` for the allowed post embeds. No `'unsafe-inline'` / `'unsafe-eval'` in `script-src`; no whole-domain wildcards. Keep the list in one config. Confirm exact hosts from violation reports. Whoever can publish in a GTM container can run any script, so limit that access (or load GA directly). Analytics should load only after cookie consent.

**HubSpot form flow (custom form, no iframe, no HubSpot script on the page)**
- Browser posts to our own service, which validates, checks spam and consent, then sends to HubSpot server-side and returns a plain result. This keeps `connect-src` tight and HubSpot code out of the page.
- Prefer the HubSpot Forms API (`/submissions/v3/integration/submit/{portalId}/{formGuid}`, authenticated variant from the server) so workflows and form reports keep working; field names must match the form's properties. Keep tokens in the service environment.
- Send consent text via `legalConsentOptions`. `hutk`, page URI and page name only help if the HubSpot tracking script is on the site.
- Save the validated submission to a queue or table first, deliver with retries, and make delivery idempotent (HubSpot rate limits; same email updates the same contact). Add rate limit, honeypot or CAPTCHA, size limits.
- File upload (CV) does not go through the Forms API. Keep Career applications separate from the HubSpot contact form (see 5a); the service now holds PII briefly, so it is inside the 5a scope, and the privacy notice must name HubSpot as a processor.

**SEO**
- CSP is not a ranking signal. The risks are indirect: slower pages (Core Web Vitals) when a nonce removes caching, broken analytics or Search Console verification, and blocked fonts, images or embeds causing layout shift or a bad Googlebot render.
- Rollout: (1) `Content-Security-Policy-Report-Only` for 1 to 2 weeks; (2) allowlist only used hosts (also `font-src`, `img-src` for the media-service origin, `style-src`, `frame-src`); (3) measure TTFB and LCP before choosing a nonce, and use a cacheable variant (host allowlist and hashes) on key landing pages if the cost is too high; (4) enforce, then watch Search Console and GA for 2 to 4 weeks; verify Googlebot rendering with URL Inspection "Live test"; verify Search Console by DNS or file, not a script.
- For SEO after leaving WordPress, URLs, 301 redirects, sitemap, titles, descriptions, canonicals and structured data matter far more than CSP.

It can be removed with `localeCookie: false`, since the URL already carries the locale (`localePrefix: "always"`).
- Admin app: sign-in token and UI preferences in `localStorage` / `sessionStorage`. Not shown to visitors, so no visitor banner.

**When consent becomes required:** as soon as non-essential cookies or storage are added: Google Analytics / GTM, HubSpot tracking (`hubspotutk`), embedded video, advertising pixels.

**Plan**
1. Before launch, inspect the real cookies and storage in a browser.
2. Consent banner with Accept, Reject (as easy as Accept) and per-category choices; store the choice and keep a consent record.
3. Load GA and HubSpot tracking only after consent; no requests to those hosts before it. Use Google Consent Mode if GTM is used. No cookie wall, no pre-ticked boxes.
4. Cookie policy page listing each cookie, its purpose and duration, with a way to change the choice later.
5. Make the CSP allowlist and consent agree (see 5b); the regional sites (Korea, Germany, Japan) have different rules.
6. Decide to build it or buy a consent-management product.
7. HubSpot server-side form submission (5b) without the tracking script sets no cookie, so it needs no consent for tracking, but the form's own consent checkbox still applies.

## 5d. Notice: form spam and bot protection (needs an update, plan only)

**Status: the current protection is not enough for public forms and must be updated before any form goes live. Not built. The plan waits for a check of the real infrastructure (CDN, WAF, load balancer, where the gateway sits).**

**Today** (`backend/gateway-service/src/main/resources/application.yaml`, `RateLimiterConfig.java`): a Redis rate limiter on every route, keyed by the server-observed remote IP (never `X-Forwarded-For`), default 20 requests per second with a burst of 40 (`GATEWAY_RATE_LIMIT_REPLENISH`, `GATEWAY_RATE_LIMIT_BURST`). chat-service has its own tighter limiter on `/v1/assistant/ask`.

**Why it is not enough for a form**
- Far too loose for a form (a bot can submit many times a minute and never be limited).
- IP is the only key: botnets and proxies stay under the limit, while offices and mobile carriers sharing one IP could block real people if the limit is tightened.
- Behind a load balancer or CDN, the gateway may see the proxy address for everyone, which puts all visitors in one bucket. Check at deployment.
- It cannot tell a human from a script and checks no content.

**Layers to plan (to decide after the infrastructure check)**
1. A tight, separate limit on form endpoints only (for example 3 to 5 per IP per 10 minutes, a daily cap, and limits per email and per phone).
2. CAPTCHA verified server-side: Cloudflare Turnstile preferred (free, privacy-friendly, mostly invisible); reCAPTCHA v3 or hCaptcha as alternatives. Add its hosts to the CSP (5b) and consider consent (5c).
3. Honeypot field, and a minimum fill time (signed timestamp, reject under about 2 to 3 seconds).
4. Server-side validation, size limits, link and spam-pattern checks, regardless of the client.
5. Origin and CSRF checks so other sites cannot post to the form.
6. Idempotency and duplicate detection (also needed for HubSpot retries, 5b).
7. Quarantine queue: save first, send to HubSpot only what passes, so spam does not pollute the CRM or use API calls.
8. Monitoring: counts of blocked and accepted submissions, spike alerts, logs without PII (5a).
9. CV upload (5a): stricter size, type and count limits, malware scan, private store, CAPTCHA required.
10. Above the gateway: a CDN with WAF and bot management (for example Cloudflare) is the best defence against distributed bots.

**Minimum for launch:** a dedicated tight rate limit, a server-verified CAPTCHA, a honeypot, validation, and the quarantine queue.

**Open:** what the current infrastructure provides (CDN or WAF, proxy headers, Redis availability), and where the form endpoint lives (see 5b).
