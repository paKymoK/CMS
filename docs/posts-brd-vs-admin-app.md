## 2. Gaps

### G1. Scheduling and Archive
- **Archive: done (posts).** Statuses are Draft, Published and Archived. Archived is off the site but kept, and can go back to Draft or be published again. The audit trail has an `ARCHIVE` action (archived back to draft is an update that lists the status change; publishing is still `PUBLISH`). **Archived posts stay editable (decision):** the status only controls whether the post is public, as with Draft and Private in WordPress, which has no built-in archived status and locks only Trash. Locking them would be a rule of our own: the server would reject content edits on an archived post and the editor would open read-only. Only posts may be archived; the server rejects ARCHIVED or any unknown status for the other content types. The Post editor has a three-way status switch, an **Archive** button (with a confirmation for a live post), **Save** and **Move to draft** for an archived post, and an "Archived" label in the list, Activity and search.
- **Public side:** an archived post answers "not found" like an unknown address and drops out of the public list and search with no read path changed (every public read matches `'PUBLISHED'` exactly). **Detail pages on the website are now fetched without Next's data cache** (`cache: "no-store"`): that cache only stores 200 responses, so a page that had been visited kept being served from its old copy after it was archived or unpublished. Lists keep the 60 s cache.
- **Schedule: done (posts), cron-based.** Statuses are now Draft, Scheduled, Published and Archived. The `active` flag is gone: status alone decides what is public (see "The `active` flag" below). See "Scheduled publishing" below.

**Scheduled publishing (built).**

- **Mechanism: pg_cron, once a minute.** The Postgres image already had pg_cron (`Dockerfile`, `postgresql.conf`: `shared_preload_libraries` and `cron.database_name = 'content'`). `init-schema.sql` now creates the extension and the job `publish-scheduled-content` (`* * * * *`, running `SELECT publish_scheduled_content()`). Once a minute was chosen over once a second to keep load low under pressure. The job is created only where pg_cron exists (the database named by `cron.database_name`); elsewhere (test databases, a managed Postgres without the extension) the schema still loads with a warning and scheduled items wait until the function is run some other way.
- **The function** `publish_scheduled_content()` moves due `SCHEDULED` items to `PUBLISHED` and due `PUBLISHED` items (with an `unpublish_at`) to `ARCHIVED`, clearing `unpublish_at`. Each direction is one `UPDATE` over a `FOR UPDATE SKIP LOCKED` selection: atomic, and a second runner skips rows the first holds. It takes everything overdue, so downtime or a missed run only delays publishing: seen live, after the machine slept for 14 minutes the job published and archived on its first run back. It stamps the write as the `System` user and bumps `version`, so Activity shows "System" and an editor with the item open gets the out-of-date-form warning.
- **Data:** `content_item.publish_at` / `unpublish_at` (timestamptz), checks (a scheduled item needs `publish_at`; `unpublish_at` must be later), and two small partial indexes so the minute check touches only waiting rows. The audit trigger has a `SCHEDULE` action and records both times (UTC) in the snapshots.
- **Rules (`ScheduleRules`):** posts only. Draft and Archived carry no times; Scheduled needs a future publish time (optional later unpublish time); a live post may have a future unpublish time. Times are kept to the minute. A time unchanged from what is stored is not re-checked against the clock, so saving in the minute before the job runs is not refused. A scheduled post without a display date is dated the day it goes live.
- **Editor:** a four-way status switch; for Scheduled a "Publish at" picker, for Scheduled and Published an optional "Take offline at" picker, with the editor's time zone shown (times are picked in it and stored as UTC). The main button reads Publish, Update, Schedule or Update schedule; publishing or scheduling a draft with SEO items missing asks once, as before. Labels for Scheduled are in the list, Activity and search.
- **Timing:** up to a minute for the job, plus the website's 60 s list cache; detail pages are not cached, so they appear as soon as the job runs.
- **Verified:** 129 content-service tests (new: `ScheduleRulesTest`, scheduling tests in `ContentAuditTriggerTest` that run the function against a real database, `StatusRulesTest`); the real pg_cron job published and archived a test row at the exact minutes; the editor was driven in a browser (schedule, SEO prompt, saved times, audit entry).
- **Browser checks, done:** on the website a scheduled post's detail page was a 404 while Scheduled, went to 200 in the same second the job ran, and was a 404 again within two seconds of its unpublish minute; the post list followed up to a minute later (its 60 s cache). The editor was checked at 820 and 390 px: the header buttons wrap, the status switch and pickers fit, nothing scrolls sideways. At 390 and 360 px the picker's popup was 515 px wide and ran off the left edge; a small-screen rule (`index.css`) now pins it to the left, lets it shrink and puts the time columns under the calendar.
- **Production:** not a concern yet, as the project has not gone live. If production Postgres is managed without pg_cron, the job must be set up there (or `publish_scheduled_content()` called by another scheduler); the schema loads either way but would only warn.
- **Still open, for later decision:** **Trash** (a deleted post goes to a Trash status with restore and a purge job) is skipped for now: Archived plus the delete rule covers it, and it needs time to decide. Other content types are not schedulable.

**The `active` flag (folded into status: done).** `content_item.active` is removed. What the public sees is now exactly `status = 'PUBLISHED'`: every public read, the search view and the full-text search dropped their `active` condition. An item that used to be inactive is simply a Draft (a post can also be Scheduled or Archived). In the admin the "Active" switches are gone from the Post, Case Study, page and list drawers; the list's old Active column is now a **Live** switch that flips Draft and Published (disabled for Scheduled and Archived posts, which are changed in the editor). The API no longer accepts or returns `active`; the audit snapshots no longer carry it. Two small behaviour changes: a case study's testimonial now shows only when the testimonial is **Published** (before, only active was checked, which the code comment already described as "unpublished quote omitted"), and restoring a version no longer restores an old active value. The seed data was unaffected (every seeded row is Published). The Banner's own "Active from / until" dates are separate fields in its data and are unchanged. The init SQL changed: recreate the local `content` database.

### G8. Delete rule and Trash
- **Delete rule: done (posts).** A published post cannot be deleted, from the API (400: "archive it or move it to draft first") or the list (the Delete button is disabled with a tooltip). Draft and archived posts can be deleted. The 051126 BRD no longer states this rule, but nothing contradicts it.
- **Trash with restore: not built, and now a stated requirement.** 051126 asks for Trash on **Posts** (POST-01: separate area, restore returns to Draft, purge after 30 days), **Categories, Tags** (30 days, restore brings back the post links), **Pages** (PAGE-02: 30 days or delete forever; listed as a status) and **Components** (CMP-03: 30 days). Today a deleted post is recoverable only through the audit trail ("Create new from this version").
- The earlier decision to skip Trash (Archived plus the delete rule) is now in conflict with the BRD; it needs a decision, see section 5.
- Sketch: a `TRASHED` status (or a `deleted_at` column) plus a purge job beside `publish_scheduled_content()` in pg_cron; the public reads already match `PUBLISHED` exactly, so a trashed row is hidden with no read path changed. The audit trigger already has DELETE and RESTORE actions.

### G10. Create a translated draft in another site (feature)
- BRD intent: when an editor drafts a post in EN, they can create a new **DRAFT** of it in another site (e.g. VI) with the content auto-translated, then review and edit it independently.
- Model stays `site == locale`. The action copies the post into the target site as a new `content_item` row (`status = DRAFT`), so the existing per-site slug rule, audit trail and access guard apply unchanged.
- Fields to translate: title, excerpt, body (HTML, tags and embeds must survive), image alt/captions, SEO fields once G4 exists. Not translated: slug is re-resolved for the target site, tags/category follow G2, media URLs and dates are copied.
- Target sites per BRD: Global → VI (auto-translate or manual upload); APAC → Thai/Chinese/Malay; Korea and Deutschland → auto from EN; Japan → manual.
- Existing building block: the "Create a new item from this version" prefill flow (`prefillAsPost`) already opens the editor on a new draft with copied content.
- A source reference on the new row (optional) would only be for display ("translated from EN post #123"), not required for the feature.

### G12. Components library and Templates (CMP-01 to CMP-04, TMP-01 to TMP-05)
- **Not built.** Blocks exist inside each page row, but there is no shared library: no list with previews, no "shared component updates every page" versus "copy that diverges" (CMP-04), no 30-day delete, no template entity with versions, "apply to all pages or only new ones", "cannot delete a template in use".
- This is the same question as section 3 of `page-model-plan.md` (embedded versus library). That plan chose embedded content with an optional library per field. ### G13. User management and security (USR-01 to USR-07)
- **Decision: user management lives in auth-service, not in the admin app.** The Users screens (USR-01 to USR-05) are built there, next to the data they change. The admin app gets no Users module. It shows a link or redirect to auth-service for a user who has permission to manage users, and hides it for everyone else.
- What auth-service has today: REST endpoints for users, groups, departments, units, clients and project-scoped role assignments (`/v1/users`, `/v1/groups`, `/v1/clients/{clientId}/roles`, and so on). Its pages are only login, consent, profile-complete and error, so the Users UI itself is still to build there.
- **Done in auth-service (backend, first slice):**
  - **Management API locked down.** `/v1/**` was open to anyone at `:9000` (and any token holder through the gateway). It is now its own filter chain (`ApiSecurityConfig`): bearer token only, no session, and only an active **Super Admin** gets in. Super Admin = the global (no site) `ADMIN` role on `cms-admin`, held directly or through a group, on an account that is not inactive. It is read from the database on each call, not from the token, so a demotion or deactivation counts at once. The seed gives `admin` the global role at startup (no DB recreate needed).
  - **Read and status API:** `GET /v1/users` (search by name / email / username, filter by status, role, site; paging, max 100), `GET /v1/users/{sub}` (with cms-admin roles, direct and through groups), `PATCH /v1/users/{sub}/status` (`ACTIVE` / `INACTIVE`).
  - **Inactive means no login.** The state lives in `userinfo.status` (an existing, previously unused column; a missing value is ACTIVE). It cannot use `users.enabled`: LDAP shadow rows are created with `enabled = false`. The login check runs after the password check, covers LDAP and local accounts, and does not count toward the lockout. Deactivating also deletes the user's `oauth2_authorization` rows so refresh tokens stop working. An access token already issued stays valid for up to 15 minutes.
  - **Last Super Admin protected** (USR-03): deactivating the user, removing the role assignment, deleting the group, or removing the member is refused if it would leave no active Super Admin.
  - **MFA (USR-05): open, seam only, not built.** The BRD names no factor, and the owner and the BA have not yet decided which to support (the email-verified activation and reset flows are not a sign-in factor). The email address is unique per account, so an email code is a cheap option when chosen. `MfaPolicy` (default `NoMfaPolicy`, always "no") is called once after a correct password in `DomainAuthenticationManager`. If a policy ever returns true, the login **fails** (no MFA step exists), it never passes. `MfaPolicy`'s javadoc says where the challenge step goes. No schema was reserved, because the factor decides the shape.
  - **Verified against real Postgres and Redis** (service started, signed in through the OAuth login): 53 API checks, covering the list filters, deactivate and reactivate, refresh-token revocation, and the last-Super-Admin refusals by user, role, group and member.
